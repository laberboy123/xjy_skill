# 反馈格式说明

配套 `kickoff-prompt.md`。这份文件是给**人**看的：解释每个字段在测什么、怎么填才有用、以及我拿到后怎么处理。

## 字段在测什么

| 字段 | 测的是 | 填错的典型 |
|---|---|---|
| `stage` | 阶段定位是否清晰 | 写"开发中"这种模糊词 |
| `skill` | 你判断自己该用哪个技能 | 写"用了几个技能"——一个阶段一个主技能 |
| `triggered_by` | **路由准确率** | 自己选的写成 named_by_human，或反过来 |
| `followed` | 遵循率 | 一律写 5（等于没测） |
| `deviation` | 具体跳了哪一步 | 写"略有偏差"——要写"跳过了 L2 的寄存器回读" |
| `gate_passed` | 门禁是否真的能判定 | 含糊写"基本通过" |
| `gate_missing` | 门禁缺哪个工件 | 空着 |
| `ambiguity` | 文本是否有歧义 | 写"没歧义"却实际猜了 |
| `gap` | 覆盖缺口 | 把"你没时间做"当成 gap |
| `satisfiable` | **门禁可满足性** | 一律 yes |
| `human_interventions` | 人的纠正成本 | 写 0（多数情况不可能） |
| `duration` | 时间成本 | 精确到分钟没必要 |

## 三类反馈，处理方式完全不同

| 类型 | 字段信号 | 我的处理 |
|---|---|---|
| **路由问题** | 多次 `triggered_by: named_by_human` | 改 `description` 触发词，不动正文 |
| **内容问题** | `ambiguity` / `gap` 有值 | 补层、改判据、加坑位 |
| **门禁问题** | `satisfiable: no` / `gate_missing` | 加退化条款或降级门禁 |

分清这三类很重要：路由问题表现为"技能没被用上"，内容问题表现为"用了但卡住"，门禁问题表现为"流程走不下去"。三者混在一起改，通常一个都改不好。

## `triggered_by` 是最值钱的一个字段

它单独决定 `description` 的质量。判断标准：

- 你说"帮我点一下这颗传感器"，agent 自己想到 `sensor-bringup` → `self`
- 你说"用 sensor-bringup 帮我点一下" → `named_by_human`

如果十个阶段里超过一半是 `named_by_human`，说明 `description` 写得不像人话，需要重写触发词——**这是我唯一没法自己测出来的东西**。

## `followed` 怎么打分才有效

不要凭感觉，按"偏离是否需要人介入"打分：

```
5  全程按层/段走，自己发现了一次偏离并拉回
4  偏离一步，自己发现并拉回
3  偏离后需要我说一句才拉回
2  需要我说多次，或连续跳过两层
1  基本没按流程，最后是我按流程手动走完的
```

**全是 5 或全是 2 都说明记录失效**。健康分布应该在 3–5 之间，且集中在 4。

## `epoch` 建议（可选）

如果项目跨多天，在块里加一行 `session: 2026-11-21 AM`，方便我判断"这个问题是第一天就出现还是后来才有"。

## 常见填错

| 错误 | 后果 | 正确做法 |
|---|---|---|
| `gap` 里写"客户需求又变了" | 这不是技能缺口，是项目常态 | `customer-spec` 的变更单就是为此设计的，写"变更单流程太重/太轻" |
| `ambiguity` 写"写得还行" | 无法改进 | 抄原句 + 你的实际理解，两者不一致才算歧义 |
| 把"没时间跑这阶段"写成 `gap` | 误判为覆盖缺口 | 写 `NA:` 原因，或 `deviation:` 跳段 |
| 一次贴 200 行聊天记录没块 | 我只能重新抽取，浪费 | 只要块，块外的用一句话补充 |
| 事后回忆补块 | 记忆会美化 | 阶段结束时当场填 |

## 我怎么消费这些块

1. **按 `skill` 分组**，看每类的 `followed` 分布和 `triggered_by` 比例。
2. `named_by_human` 集中的技能 → 重写 `description`（不改正文，避免影响已经能触发的场景）。
3. `ambiguity` 逐条对照原文 → 改那一句，不整段重写。
4. `gap` 里跨项目重复的 → 加层/加坑位；只出现一次的 → 记 inbox 观察。
5. `satisfiable: no` → 加退化条款，并同步改 `workflow.md` 的门禁表。
6. 改动前后跑 `evals/cases.md` 的 24 条，命中率不能降。

## 验证有效的最低标准

一个项目跑完，如果这四件事有明确结论，这次验证就算成功：

1. 十个技能里哪几个**从没被 trigger**，为什么
2. 哪几条门禁**真的拦住过问题**（有具体事例）
3. 哪几条判据**在你的项目里不成立**（`satisfiable: no`）
4. 哪个阶段的**人工介入次数最多**（成本最高的地方）

有这四条，我就能改出第二版；没有，说明记录得太粗。
