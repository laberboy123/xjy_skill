# 板级测试（board test）

## 概述

嵌入式测试最容易走成两种极端：要么"全部靠手点"，要么"等有硬件了再测"。两者都很贵。

正确的结构是**分层**，而且**从上往下 ROI 递增**：

| 层 | 测什么 | 依赖硬件 | 什么时候能开始 |
|---|---|---|---|
| **T0 主机侧单元** | 协议解析、状态机、单位换算、滤波算法、CRC | 否 | 拿到 spec 就能写 |
| **T1 驱动 HIL** | 驱动在异常下的行为（NACK、超时、错寄存器、丢帧） | 否（mock 总线） | 有接口就能写 |
| **T2 板级集成** | 上电→初始化→自检→跑 30 分钟→断电，自动出报告 | 是 | 有板子 |
| **T3 场景/验收** | 客户用例、物理激励、人机交互 | 是 | 有整机 |
| **T4 回归/长稳** | 8h/24h soak、掉电重启、错误注入、温漂 | 是 | 每次发版前 |

T0/T1 是你在"等板子"和"板子还没调通"期间唯一能推进的事，也是唯一能在 CI 里跑的部分。**先建 T0/T1，再谈其他。**

## 何时使用

- 新项目开工，要定测试策略
- 项目没有回归用例，每次改完靠手点
- 上位机只有 GUI 按钮，测试无法复现、无法自动化
- 交付前要出测试报告
- 怀疑改动破坏了老功能

## 核心设计决定：把总线抽象成 ops

这一条现在不做，后面所有自动化都要重来。（`bus_ops` 接口由 `design-budget` D3 产出，本技能是消费方。）

```c
/* bus 抽象：驱动只依赖这组函数指针，不依赖具体平台 */
struct bus_ops {
    int (*read)(void *ctx, uint8_t reg, uint8_t *buf, size_t len);
    int (*write)(void *ctx, uint8_t reg, const uint8_t *buf, size_t len);
    void *ctx;
};

struct sensor_dev {
    const struct bus_ops *bus;
    uint8_t addr;
    /* ……器件状态 */
};

/* 板子上：真实 I2C/SPI 实现 */
int i2c_bus_read(void *ctx, uint8_t reg, uint8_t *buf, size_t len);
/* PC 上：mock 实现，可注入错误 */
int mock_bus_read(void *ctx, uint8_t reg, uint8_t *buf, size_t len);
```

有了这层，同一个 `.c` 文件既能在目标板上跑，也能在 PC 上编译跑单测——**驱动代码不再需要"上板才知道对不对"**。

配套要求：

- 驱动里所有阻塞点必须有超时返回，错误码统一（0 成功 / 负值错误），不要用 `while(1)` 等标志位。
- 所有硬件相关调用（延时、日志、临界区）也做一层薄封装，PC 上可以替换。
- 业务逻辑（状态机、判定、换算）与寄存器操作分离，前者纯函数化，才好测。

## 流程

### Step 1：列 T0 用例

按"纯逻辑 + 无硬件依赖"筛：

- 帧解析：正常帧、长度错、CRC 错、粘包、半包、超长帧
- 状态机：所有合法迁移 + 所有非法迁移都被拒绝
- 单位换算：量程边界、负值、溢出、NaN 类异常
- 判定逻辑：阈值、迟滞、防抖

工具：Unity / Ceedling / 或最小 `assert.h` + 一个 `main`，能跑就行，别在工具链上纠结。用 `make test` 一条命令跑完，目标是能进 CI。

### Step 2：列 T1 用例（故障注入）

这是最值钱的一层。用 mock 总线逐个注入：

| 注入 | 期望行为 |
|---|---|
| 每次读都返回 NACK | 初始化失败并返回明确错误，不进入就绪态 |
| 第 N 次读超时 | 重试策略生效，超过阈值后报错并降级 |
| 返回的 ID 不匹配 | 拒绝初始化，不带着错配置继续跑 |
| 数据长度短于预期 | 丢弃该帧，不越界 |
| 长时间无数据（断线） | 上层收到超时，看门狗/降级策略触发 |
| 错误后恢复正常 | 能自动恢复，不需要重启 |

每个用例都要断言"返回值 + 状态机状态 + 副作用"，不要只断言返回值。

### Step 3：让 T2 可脚本化

T2 的目标是"一条命令跑完整个上电自检并出报告"。要求：

- 板子开机打印结构化输出（或通过上位机读），内容包括：固件版本、每个器件的 ID/状态/通信错误计数
- 一条脚本完成：烧录 → 上电 → 等就绪 → 跑自检 → 采集 N 分钟数据 → 断电 → 生成报告
- 报告里有：通过/失败项、失败项的证据（原始 log 片段）、耗时

### Step 4：让上位机可脚本化（关键）

**上位机不要只有 GUI 按钮。** 加一条文本命令通道（串口或网口），JSON lines 或 `cmd arg` 都行。设计见本技能目录的 `host-protocol.md`；定稿后复制到项目 `docs/host-protocol.md`。

最低要求：

```json
{"cmd":"id"}                                  → {"ok":true,"fw":"1.2.3","sn":"..."}
{"cmd":"read","addr":"0x68","reg":"0x75"}     → {"ok":true,"data":[0x68]}
{"cmd":"stream","ch":"accel","ms":100}        → {"ok":true,"n":100}
{"cmd":"inject","target":"i2c","mode":"nack"} → {"ok":true}
```

同一个通道，人可以在 GUI 里点，脚本可以 `send + parse`。这一条把上位机从"演示工具"变成"测试夹具"，T2/T3 才算真正成立。

### Step 5：T3 对齐客户用例

把 spec 第 1 段（验收定义）里的每条客户操作，逐条转成：

```
用例编号 | 前置状态 | 操作步骤 | 预期现象 | 判定方式（人看/脚本判） | 实际结果
```

判定方式优先选脚本能判的（数值、报文、状态位）；只有"外观、声音、手感"这类才留给人。**能脚本判的不要留给人。**

### Step 6：T4 长稳与回归

每次发版前跑：

- 8h 或 24h soak：数据不断、内存不涨、总线错误率为 0
- 掉电重启 20 次：每次都能自恢复
- 错误注入组合：总线错误 + 传感器拔插 + 通信中断
- 温漂：如果有条件，高低温各跑一轮

记录：运行时长、总帧数、错误帧数、峰值内存、重启次数。

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "等有硬件再测" | 等硬件的时间是纯浪费 | 先写 T0/T1，它们不需要硬件 |
| "驱动没法单测，都是硬件操作" | 因为没做 bus 抽象 | 先花半天做 ops 抽象，之后一直受益 |
| "上位机是给客户看的，不用能跑脚本" | 你自己就是它最大的用户 | 加一条文本命令通道，成本很低 |
| "手点一遍也就十分钟" | 每次发版十分钟 + 不可复现 + 漏项 | 十分钟能变成十秒且可回归 |
| "这个 bug 修完就好了，不用加用例" | 下次还会回来 | 每个修掉的 bug 补一条用例，这是唯一让测试变强的机制 |
| "测试覆盖率低说明测试没用" | 覆盖率低说明测的地方不对 | 测行为不测实现，从接口层测 |

## 红旗

- 上位机所有操作都只能通过点击完成
- 修完 bug 没有补用例
- 回归靠"我记得之前测过"
- 测试报告是手写的
- 驱动和业务逻辑在同一个文件里，无法单独编译
- 板子没有自检输出，出问题只能靠人拆开看

## 验收（测试体系可以交付了）

- [ ] `make test` 一条命令跑完 T0，全部通过
- [ ] T1 覆盖 6 类故障注入，每类都有断言
- [ ] T2 一条脚本从烧录到出报告全程无人干预
- [ ] 上位机提供文本命令通道，且有脚本示例
- [ ] T3 用例与 spec 第 1 段逐条对应，无遗漏
- [ ] T4 有明确的时长标准和判定指标
- [ ] 最近 3 个 bug 都已补用例

## 使用后沉淀（每次都用）

每轮测试结束（尤其是"测出来一个没想到的失败"之后），记一行到 `learnings/inbox.md`：

```
2026-11-20 | board-test | T1 | STM32L4 + SHT40 | 现象：注入 NACK 后驱动死等 8s 才超时 | 证据：log 时间戳 | 建议：T1 加"每个阻塞点超时≤100ms"断言 | 信心：高
```

重点记两类：

1. **用例没覆盖到的故障模式**——测出来才发现的，直接进 T1 用例表候选。
2. **判定方式选错了**——本可以脚本判却留给人判，或反之。

新用例先追加到 `learnings/inbox.md`，累积后由 `skill-curator` 提案并入 `test-plan.md`；已确认有效的可以直接补进你自己的项目测试计划，不必等提案。
