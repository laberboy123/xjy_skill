# 需求收件与抽取（requirement intake）

## 概述

客户给的是文件，不是需求。中间要做一步转换：**把文件里的事实抽成条目，而不是把文件读一遍写个摘要。**

区别很实在：

| 摘要式阅读 | 条目式抽取 |
|---|---|
| "支持温度采集，精度 ±0.5℃" | `R-012｜±0.5℃ @ 25℃｜参数｜需求书.pdf p.7 表2｜可判定` |
| 丢了出处，后面扯皮没依据 | 每条能回到原文页码 |
| 冲突发现不了 | 正文与表格不一致时自动暴露 |
| 缺什么看不出来 | 对着十段清单标缺口 |

摘要式阅读会在三个地方让你付代价：数字记错、出处丢失、冲突忽略。而这三样恰好是嵌入式返工的主要来源。

## 何时使用

- 客户给了需求书 / 技术协议 / 参数表 / 招标文件（pdf、docx、xlsx）
- 需求散在聊天截图、邮件、会议纪要里
- 要复用旧项目的需求文档做新项目
- 需求变更后给了新版文档

**不适用**：需求已经是一份结构清晰的 spec（那直接用 `customer-spec` 的复用条款）；纯口头需求（走访谈，不进本技能）。

## 格式分诊（先判断能不能读）

| 格式 | 抽法 | 陷阱 |
|---|---|---|
| md / txt | 直接读 | 无 |
| docx | `pandoc -t gfm` 或 python-docx；**表格必须单独抽** | 参数常在表格里，只读正文会漏 |
| pdf（有文本层） | `pdftotext -layout` | 双栏排版会串行；扫描件抽出来是空白或乱码 |
| pdf（扫描件） | `pdftoppm` + `tesseract` OCR | 数字和单位最容易 OCR 错（0/O、1/l、±、µ） |
| xlsx | openpyxl / pandas 读全部 sheet | 合并单元格、单位行、注释行会被当成数据 |
| 图片/截图 | OCR | 必须先人工核对关键数字再采信 |

先用一条命令判断 pdf 类型：

```bash
pdftotext -layout input.pdf - | head -40    # 有内容 = 文本层可读；空白/乱码 = 扫描件
```

判断结论要写进条目表头：`来源类型: 文本层 / OCR（需核对）`。

## 流程

### I0 存量盘点

列一张文件清单，每个文件记：文件名、页数/表数、来源类型（文本层/OCR）、版本或日期。

同一份需求给了多个版本时，**先确认哪份有效**，不要合并——合并会产生无法归因的冲突。

### I1 抽条目（不是抽段落）

抽取单元是"**一条可判定的需求**"，六字段：

| 字段 | 说明 |
|---|---|
| ID | `R-001` 顺序编号，后面 spec 引用它 |
| 原文要点 | 可截断，但数字和单位必须完整 |
| 出处 | `文件名 p.页码 / 章节号 / 表名`——没有出处的条目不算条目 |
| 类型 | 功能 / 参数 / 时序 / 协议 / 异常 / 验收 / 约束 |
| 可判定 | 是 / 否（否 → 标"需澄清"） |
| 备注 | 歧义点、单位换算、疑点 |

硬规则：

- **不可判定的原样保留**，标"需澄清"，**不许自己补全**。
- 数字、单位、量程、周期、超时值，一律照抄，不做"合理推测"。
- 一条原文里含多个独立要求时，拆成多条。后续能合并，但拆不开就永远分不清。

### I2 冲突检测

同一对象在多处出现且不一致，列冲突表：

| 编号 | 对象 | A 处说法 | B 处说法 | 初步判断 |
|---|---|---|---|---|
| C-01 | 上报周期 | 正文 p.3：5s | 表 4 p.9：10s | 待客户确认 |

高频冲突点：正文 vs 表格、主文档 vs 附件、需求书 vs 协议文档、新版 vs 旧版、文字 vs 图示。

**不要自己选一个信。** 冲突是访谈的第一优先级。

### I3 缺口检测

对着 `customer-spec` 的十段标"有 / 无 / 不完整"：

| 段 | 状态 | 说明 |
|---|---|---|
| 1 验收定义 | 无 | 文档只写功能，没写怎么判定 |
| 5 实时性 | 不完整 | 有周期，没死线 |
| 8 异常策略 | 无 | 完全没提失效行为 |

经验：客户文档最常缺的就是 **1（验收）、5（实时性）、8（异常）**。这三段几乎总要靠访谈补，不要指望原文里有。

### I4 输出

`docs/requirements-extracted.md`，四块：文件清单、条目表、冲突表、缺口表。模板见 `requirements-table.md`。

### I5 交给 customer-spec

关键收益在这里：**访谈只问冲突项和缺口项**。

- 不问已经有答案的（那是浪费时间，客户会觉得你没读文档）
- 冲突项逐条问："文档第 3 页说 5s，第 9 页表格说 10s，哪个对？"
- 缺口项带推荐答案问："异常时是报警还是静默降级？我建议报警，你确认"

这样一轮访谈通常能从"两小时从头问"压到"二十分钟确认十几个点"。

## 抽全性验证（做完必查）

抽取最大的风险是"以为抽全了"。三个机械检查：

1. **数字反查**：grep 文档里所有数值+单位（`[0-9.]+\s*(ms|s|mA|µA|V|℃|Hz|kbps|bit)`），逐个数是否都进了条目表。漏的通常是表 4 第 7 行那种角落参数。
2. **表格覆盖**：docx/xlsx 的每一张表，必须至少产出一条条目；没有就说明表没被读。
3. **随机页抽查**：随机挑 3 页，人工核对"这一页所有可判定要求是否都在表里"。抽不全就重抽，别往下走。

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "我读一遍总结一下" | 摘要必丢数字和出处，后面无法回溯 | 抽条目，逐条带页码 |
| "扫描件读不了，等客户给电子版" | 可能永远等不到 | OCR + 人工核对关键数字，标注来源类型 |
| "表格太复杂，先按正文来" | 参数往往只在表格里 | 表格单独抽，漏表等于漏需求 |
| "文档没写就是没有要求" | 没写 ≠ 不需要，是缺口 | 标缺口，访谈确认 |
| "两处不一致，按新的算" | 你不知道哪个是新的 | 列冲突，问客户 |
| "这个明显是笔误，我改过来" | 你的"明显"可能是客户的真需求 | 原样保留 + 标疑点 |
| "客户口头补的不算文档" | 口头承诺最容易反悔 | 进假设台账，不进需求条目 |

## 红旗

- 条目表里有条目没有出处
- 文档里出现过的参数，条目表里找不到
- 有 docx/xlsx 但没有任何表格类条目
- 冲突表是空的（多半是没比，不是真没冲突）
- OCR 结果未核对就写进条目
- 缺口表是空的（客户文档几乎不可能十段齐全）
- 把"需澄清"的条目自己补成了确定值

## 验收（可以交给 customer-spec 了）

- [ ] 文件清单完整，标了来源类型（文本层/OCR）与版本
- [ ] 每条条目有 ID、原文要点、出处、类型、可判定标记
- [ ] 数字反查通过：文档里的数值参数全部进表
- [ ] 每张表格都有对应条目
- [ ] 随机 3 页抽查通过
- [ ] 冲突已列，且没有自行裁决
- [ ] 缺口对照十段已标（1/5/8 段重点查）
- [ ] OCR 来的数字已人工核对，并在备注里注明
- [ ] 输出在 `docs/requirements-extracted.md`

## 使用后沉淀（每次都用）
