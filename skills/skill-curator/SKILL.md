# 技能维护（skill curator）

## 概述

这套技能要能**在使用中自己变好**，但不能失控。区别在于分两件事：

- **捕获**可以全自动——看到值得记的就记，没有风险。
- **改判据**不能自动——一次偶发会被写死成"真相"，之后一直误导人。

所以设计成四层，风险逐层升高：

| 层 | 动作 | 谁做 | 是否改动 SKILL.md |
|---|---|---|---|
| **T0 捕获** | 追加一行到 `learnings/inbox.md` | agent，自动 | 否 |
| **T1 提案** | 聚类、生成 diff、写进提案区 | agent，自动 | 否（只生成） |
| **T2 批准** | 看 diff、跑 evals、合并 | **人** | 是 |
| **T3 整理** | 去重、抽象、压缩、退役 | 人 + agent | 是 |

这条边界和 pstack 的"写代码的 agent 不能自己判自己过"是同一个道理：**判据是这个技能的真相，真相不能由产生它的那一次实验自己宣布成立。**

## 路径解析（先做这一步）

`learnings/` 和 `evals/` 是仓库级目录，但技能可能被单独安装到别处。按顺序找，找到第一个就用：

1. 环境变量 `EMBEDDED_SKILLS_HOME` 指向的目录
2. 本技能所在仓库的根（`SKILL.md` 往上两级或三级，看得到 `learnings/` 的那层）
3. `~/.embedded-skills/`（不存在则创建，并告知用户）

路径确定后，本次会话内固定使用，不要中途切换。

## T0：捕获（每次使用后都做）

> 日常由 `capture-learnings` 在会话收尾时自动完成，不需要用户提醒。本节定义格式与标准，两者共用。

### 什么时候记

出现下面任意一条，就记一行：

1. **判据失效**：判据说"通过"，但后面出了事（该拦没拦）
2. **判据误拦**：判据说"会挂"，实际没事（误拦）
3. **未被覆盖**：出现了现有分层/段落没描述的现象、器件、平台差异
4. **有效经验**：某个"5 分钟判断法"被验证有效（**正面样本也要记**，否则技能只会越来越保守）
5. **反复出现的纠正**：同一个错误被你自己或客户纠正了第二次

不记：一次性的偶发、和判据无关的环境噪音、别人的项目八卦。

### 记成什么样

一行，管道分隔，可 grep：

```
日期 | 技能 | 层/段 | 平台或器件 | 现象 | 证据 | 建议动作 | 信心
```

示例（真实条目会更长，但保持一行）：

```
2026-11-20 | sensor-bringup | L2 | SPI / BMP390 | ID 读到 0x00 | MISO 无驱动，示波器 w3.png | 坑位表加"MISO 浮空" | 高
2026-11-20 | customer-spec | 第8段 | 冷链 | 客户没想过断网怎么办 | 访谈记录 11-20 | 第8段预填"断网>5min 本地缓存+补传" | 高
2026-11-20 | board-test | T1 | SHT40 | 注入 NACK 后死等 8s | log 时间戳 | T1 加"阻塞点超时≤100ms" | 中
```

字段要求：

- **现象**：可观测，不带解释
- **证据**：文件名或实测值，没有证据就写 `无` 并把信心标 `低`
- **建议动作**：加判据 / 改判据 / 加坑位 / 加用例 / 预填模板 / 删除某条
- **信心**：高（有实测）/ 中（有推断）/ 低（只有印象）

### 不要做什么

- 不要为了"记录完整"去写长文——inbox 是待办队列，不是文档
- 不要修改 inbox 里已有的行（除了把状态从 `待议` 改成 `已提案`/`已拒绝`）
- 不要把这些内容塞进 `SKILL.md` 正文，否则每次加载都变贵

## T1：提案（自动，但只生成）

每周或攒够 5 条未处理条目时，做一次聚类：

1. 按 `技能 + 层/段` 分组
2. 同一组内相同模式的条目合并成一条"类"
3. 每个类判断是否达到提升门槛（见下），达到的生成提案

### 提升门槛（两个条件满足其一）

- **复现**：同一个类在 **2 个以上不同项目或不同器件**上出现过
- **严重**：单次发生但造成 **≥1 天返工**、交付事故、或客户投诉

达不到门槛的，留在 inbox 标 `观察中`，不要动 SKILL.md。**单次事件是噪声，重复才是信号。**

### 提案格式

不要把提案写成"我觉得应该加一条"。写成可以直接应用的 diff：

```
提案 P-003
目标：skills/sensor-bringup/SKILL.md，L2 表格"不通过时"一列
理由：inbox #12 #19 两次复现（BMP390 / ICM42688），MISO 浮空时读到 0x00，现有判据只写了 0xFF
变更：
  - | 不通过时 | 查地址脚/CS |
  + | 不通过时 | 读到 0xFF 查地址脚/CS；读到 0x00 且 MISO 无驱动时查器件供电与 CS |
回归：跑 evals/cases.md 第 2、7 条
```

提案写进 `learnings/inbox.md` 的"提案区"，然后**停下来等人批准**。

## T2：批准（人来拍板）

人看三件事：

1. 理由是否有证据（不是"感觉"）
2. diff 是否只改了必要的部分（不要顺手重写整段）
3. 跑 `evals/cases.md`，命中率不能下降

合并后：

- 更新 `CHANGELOG.md`（版本号 + 一句为什么）
- 把 inbox 对应条目状态改成 `已合并 vX.Y.Z`
- 如果这次改动让某条旧判据失去意义，同时删掉它

### 为什么不许 agent 自己改

判据被一次偶发污染后，它会在之后每次使用中误导人，而且**没人会再检查它**——因为大家都假设技能库是"沉淀过的"。这种错误比"没有判据"更贵。

## T3：定期整理（每月一次，30 分钟）

技能只会越来越长，除非主动删。每月做四件事：

1. **去重**：同一条规则在多个技能里重复 → 抽成一处，其它地方引用
2. **抽象**：三个具体坑能归纳成一条通用判据 → 合并（但保留具体例子作为证据）
3. **压缩**：SKILL.md 超过 200 行就有问题了，砍掉案例、保留判据；案例移到同目录的 reference 文件
4. **退役**：满足下面任意一条的判据，**提案删除**
   - 90 天内零命中，且没有证据支撑它曾经有用
   - 误报率高于命中率（每次都在报，但大多数是假警报）
   - 被更好的判据完全覆盖

退役和新增同样重要。一个只会长大的技能库，最后会贵到没人加载。

## 一次性回填（bootstrap）

新装这套技能时，inbox 是空的。**agent 不知道你过去半年卡过什么**，所以要做一次回填，两种方式可以并用：

### 方式 A：访谈式（20 分钟）

一次只问一个问题，每问带推荐答案：

1. "过去半年你卡最久的一次是哪个器件？卡了几天？最后是什么原因？"
2. "有没有哪次是'看起来通了，交付后才发现不对'？"
3. "有没有哪颗器件你到现在也不确定它是不是真的对？"
4. "客户需求里，哪一类问题最常返工？"
5. "有没有哪次改动破坏了老功能，而且测试没抓到？"

每个答案整理成 1–3 行 inbox 条目。**不要追问细节到疲惫**，够写一条就够。

### 方式 B：挖历史（有材料时）

如果能拿到下面任意一种，让 agent 批量挖掘：

- 旧的聊天记录 / 工作日志
- git commit message（`fix:`, `debug:`, `临时` 这类关键词）
- 测试报告、bug 列表、客户邮件
- 之前的经验笔记

挖掘指令：

> 从这些材料里找出"卡住超过半天"的事件，按 skill-curator 的格式输出 inbox 条目；只保留有明确现象和根因的，其余标 `信心：低`。不要编造原因。

回填完成后，第一次 T1 提案通常会一次提升十几条——这是正常且值得的。

## 与 evals 的配合

`evals/cases.md` 是一小组"给现象，问该判到哪一层、下一步做什么"的固定题。作用只有一个：**防止改动让技能变差**。

规则：

- 任何 T2 合并前必须跑一遍
- 命中率下降 → 回滚这次改动，不要"再改改看"
- 每季度补充 2–3 个新 case（从真实事故里来）

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "这个坑我刚踩过，直接写进 SKILL.md 吧" | 一次是噪声，写进去会误导以后每一次 | 先记 inbox，等第二次复现 |
| "记了也没人看" | 提案是从 inbox 生成的，不看就永远不改进 | 每周花 5 分钟过一遍 |
| "技能越全越好，都留着" | 每一条都占 context，还稀释注意力 | 90 天零命中的提案退役 |
| "让我自己改，人审太慢" | 判据被污染的成本远高于审一次 diff | T2 必须是人 |
| "这个经验只对这颗芯片有用，不用记" | 底层通常通用（时序/地址/回读），只是还没抽象 | 往上抽一层再记 |
| "跑 evals 太麻烦" | 没有回归的技能库改几次就不可信了 | 至少跑命中率最高的 10 条 |

## 红旗

- `learnings/inbox.md` 超过 30 条未处理
- SKILL.md 连续 3 个版本只增不减
- 有提案但没有"证据"字段
- 同一个坑被记进 inbox 三次，却从没提案
- 改了 SKILL.md 但 CHANGELOG 没动
- agent 直接编辑了判据表格，没有 diff、没有批准记录

## 验收（一次维护循环完成）

- [ ] 本次会话的新发现已进 inbox，每行有证据字段
- [ ] 达到门槛的类已生成带 diff 的提案
- [ ] 提案已跑 `evals/cases.md`，命中率未下降
- [ ] 合并的改动已更新 `CHANGELOG.md` 版本号
- [ ] inbox 中已处理条目状态已更新
- [ ] 本月退役评审已做过（哪怕结论是"没有可退役的"）
