# 经验回收（experience retro）

## 概述

"工作内容变成经验和简历转化率低"不是因为你没做事，而是缺一个**中间层**：做完就过去了，没有把"这次怎么解决的"变成"下次怎么更快"，也没有把"我做了什么"变成"带来了什么可测变化"。

中间层就是**经验卡**，六格，十分钟填完：

```
现象     ——  发生了什么（可观测，不带解释）
定位路径 ——  哪一层/哪一步切下去的，用了什么证据
根因     ——  真正的原因（不是"改好了"）
修复     ——  改了什么（代码/配置/流程）
可复用规则 ——  下次遇到同类，5 分钟内怎么判断
证据物   ——  波形/寄存器快照/log/报告/demo
```

填完走两条出口：**回写技能库**（复利）和**写简历条目**（变现）。

## 何时使用

- 一个卡点刚解决（趁热，超过一天记忆就开始美化）
- 一个项目收尾或交付
- 每周五固定 20 分钟
- 准备简历、面试、绩效自评
- 同类问题第二次出现（说明第一次没沉淀下来）

## 流程

### Step 1：趁热记现象

在问题解决后的**当天**写下现象，趁记忆还没被"我早就想到了"污染。

要求：

- 写可观测事实，不写解释。"读 ID 返回 0xFF" 是现象；"芯片坏了" 是解释。
- 带上数字：耗时多久、改了几版、试了几个方向。

### Step 2：还原定位路径

这是整张卡最有价值的一格，也是最容易漏的一格。回答：

- 从哪一层开始查的？为什么从这层开始？
- 哪一次测量/实验让范围缩小了一半？
- 有没有一次"以为是 A，结果是 B"的转折？转折靠什么证据？

如果写不出"哪一步切下去的"，说明当时是运气，不是方法——那这次的收获就是"建立方法"，把这句也写进去。

### Step 3：填根因和修复

- 根因要能解释**所有**现象，不只是主症状。解释不了的，说明还没到底。
- 修复要区分：改代码 / 改配置 / 改流程 / 改工具。**改流程和改工具的收获通常比改代码大**，因为它们会一直起作用。

### Step 4：提炼可复用规则（关键一步）

规则必须是**下次能直接执行的判断句**，不是感想。

| 不合格 | 合格 |
|---|---|
| 以后要注意上拉电阻 | I2C 读 0xFF 时先量 SCL 上升时间，超过 300ns 直接换 2.2k 上拉，不要动驱动 |
| 要仔细看 datasheet | 换料后第一件事是 dump reset 寄存器快照，和 datasheet reset value 逐项比对，差异项就是坑 |
| 多沟通 | 客户说"简单"时，先要一句可判定的验收标准，否则不估算工期 |

判据：把这条规则给一个不认识你的人，他能不能照着做？

### Step 5：回写技能库

按规则的性质分流：

- 属于"怎么点亮" → 写进 `sensor-bringup` 对应层的判据，或它的 `layered-bringup.md` 坑位表
- 属于"怎么测" → 写进 `board-test` 的用例或红线
- 属于"怎么谈需求" → 写进 `customer-spec` 的问题库
- 属于"工具/环境" → 例如"这台机器的 i2cdetect 要加 -r""这个 BSP 的 pin 上拉必须查 pinctrl"，写进自己的环境说明

**每张卡至少产出一条规则。** 没有规则说明还没提炼到位。

### Step 6：写简历条目

结构固定：**机制 + 可测变化**。不是"负责什么模块"，而是"做了什么机制，带来什么变化"。

句式：

> [动词] + [对象] + [用的方法/机制]，[量化结果]

嵌入式好量化的指标，挑你真有的写：

| 类别 | 指标 |
|---|---|
| 效率 | 点亮耗时（天/颗）、单轮全测时长、发版周期 |
| 质量 | 一次通过率、回归用例数、现场故障率、返修率 |
| 性能 | 采样率、启动时间 ms、响应延迟、抖动 |
| 功耗 | 平均电流 mA、待机电流 µA、续航 |
| 稳定 | 长稳小时数、丢帧率、误码率、重启恢复成功率 |
| 规模 | 支持器件数、代码行数/模块数、通信协议数 |

示例：

> 建立传感器分层点亮流程（L0–L6 判据 + 最小验证固件 + 证据日志），把 6 类器件的平均点亮周期从 3 天压到 1 天内，返修板复测从"重头查"变为按层 30 分钟定位。

> 为温控项目搭建 T0–T4 测试体系：主机侧单测覆盖协议解析与状态机（80+ 用例）、mock 总线注入 6 类故障、板级脚本化自检一条命令出报告，发版前回归从 2 小时手工降为 8 分钟自动。

> 设计上位机文本命令协议（JSON lines over UART），使测试从手工点击变为可脚本、可复现、可进 CI，单轮全功能验证从 2 小时降到 20 分钟。

反例（不要这么写）：

- "负责传感器驱动开发" —— 没有机制，没有结果
- "使用 C 语言在 RT-Thread 上开发" —— 这是环境，不是成果
- "解决了多个疑难问题" —— 无法验证
- "提升了系统稳定性" —— 没有数字

### Step 7：存证据

建一个目录（本地或网盘），按项目分：

```
evidence/
└─ 2026-11-温控项目/
   ├─ waveforms/        波形截图（标注测量点与结论）
   ├─ regs/             寄存器快照 dump
   ├─ logs/             关键 log
   ├─ reports/          测试报告
   └─ demo/             演示视频/上位机截图
```

面试时"我能给你看当时的波形"比任何描述都强。**证据要在项目期间存，别等要用了再翻。**

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "解决了就过去了，还写什么" | 不写就只剩模糊记忆，下次重走一遍 | 十分钟，当天写 |
| "这个经验只对这颗芯片有用" | 通常底层是通用的（时序、地址、回读），只是你还没抽象 | 往上抽一层再写 |
| "简历等找工作时再整理" | 到时候你只记得最近三个月 | 每个项目收尾就写 2–3 条 |
| "没有量化数据" | 多半是没记，不是没有 | 下次项目开始就记：耗时、通过率、功耗 |
| "写太细了没人看" | 是给你自己和面试官看的，不是给评审看的 | 现象写细，结论写短 |
| "是别人帮我解决的" | 那你的收获是"怎么让别人更快帮到你"，这也是经验 | 写协作路径，别装作独立解决 |

## 红旗

- 一张卡填完，没有任何一条"下次 5 分钟怎么判断"
- 简历条目里出现"负责""参与""协助"但没有结果
- 同一个坑第三次踩（说明回写没做）
- 证据物一栏空着
- 只有结论没有定位路径

## 验收（一张卡完成了）

- [ ] 现象是可观测事实，带数字
- [ ] 定位路径里有至少一次"缩小范围"的关键动作
- [ ] 根因能解释所有现象
- [ ] 至少一条可执行的可复用规则（别人能照着做）
- [ ] 规则已回写进对应技能文件（不是只写在卡里）
- [ ] 一条简历条目，含机制 + 量化
- [ ] 证据物已归档到项目目录

## 使用后沉淀（每次都用）

经验卡本身就是沉淀，但有两类东西要单独记进 `learnings/inbox.md`，因为它们会反哺其他技能：

```
2026-11-20 | experience-retro | 规则 | 通用 | 现象：同一类 I2C 死锁第三次出现 | 证据：三张经验卡 | 建议：把"9 脉冲解锁"从经验卡提升为 sensor-bringup L5 必做项 | 信心：高
```

记的两类：

1. **同一个规则在三个以上项目里都用到**——它该从"经验卡"升级为"技能判据"。
2. **简历条目写不出量化**——说明这个项目的指标一开始就没记，该回头补记录习惯（这条反过来会改进 `board-test` 的报告字段）。

升级动作走 `skill-curator`，不要自己改判据。
