# 现场支持（field support）

## 概述

现场问题最贵的不是修，是**往返**：客户说"不能用"，你说"再试试"，来回三天，最后发现是他把电源接反了——或者更糟，你改了三版代码，问题还在。

两个原则：

1. **没有信息包，不许开始归因。** 靠客户描述改代码，等于蒙着眼睛改。
2. **先分清单机 / 批次 / 环境 / 操作。** 这台坏、这批坏、这个环境坏、这种用法坏——四种情况的处置完全不同。

借 agent-skills observability 的一条思路：**先写清"值班的人会问哪几个问题"，再决定记什么**。你记的每一条日志/计数，都应该能回答其中一个问题。

## 何时使用

- 客户报障，但描述模糊（"偶尔死机""数据不准"）
- 同一问题出现第二台设备
- 返修件换了板子还是同样现象
- 需要判断能否现场规避、是否停用
- 修复后要确认"真的修好了"

**不适用**：实验室里自己写的 bug（直接调，用 `sensor-bringup` 或 `code-audit`）。

## 流程

### F0 先要信息包（最小复现集）

一次性收集，别挤牙膏：

| 项 | 为什么必须 |
|---|---|
| 固件版本 + git SHA + hwrev | 否则不知道在讨论哪份代码 |
| SN / 批次 / 出厂日期 | 决定是否批次问题 |
| 复位原因（寄存器或黑匣子） | 区分死机、看门狗、掉电 |
| 运行时长（到故障） | 区分上电即坏与长跑坏 |
| 错误计数（通信/超时/CRC） | 定位到模块 |
| 最近 N 条事件 | 看到故障前的动作序列 |
| 配置快照 | 排除配置差异 |
| 供电电压 / 温度 / 环境 | 排除环境 |
| 客户操作描述（做了什么、多久一次） | 排除操作与用法 |
| 是否可复现、复现条件 | 决定下一步 |

实现方式（至少有一种）：

- 固件内 `diag` 命令，一条命令吐出全部（推荐）
- 上位机一个"导出诊断包"按钮
- 日志文件导出到 U 盘/SD

判据：**这份包能不能让没见过现场的人写出一份复现步骤？** 不能就补字段。

### F1 黑匣子（上电就要有，不是出事才加）

没有黑匣子的产品，现场问题只能靠猜。

- **环形缓冲**存最近 N 条事件（N 建议 ≥ 64），掉电保存到 flash 或备份 RAM。
- **事件 ID 化**：不是自由文本，是稳定编号 + 参数（`EV_I2C_NACK(addr, reg)`），这样才能统计和聚类。
- 记录：复位原因、启动次数、每次启动的版本、关键状态迁移、错误码、异常前后的时间戳。
- 判据：**能回答"复位前最后 10 个事件是什么"**。答不出来，现场支持就是盲的。

### F2 归因：四级分类

先分类，再动手：

| 级别 | 特征 | 判定方法 | 处置方向 |
|---|---|---|---|
| **单机** | 只有这一台 | 同批次其它正常；换板/换件后消失 | 返修、换件 |
| **批次** | 同 SN 段或同产线时间集中出现 | 按 SN/出厂日期聚类；对比"好的机器" | 停线排查、批次召回 |
| **环境** | 特定温度/供电/EMC/安装位置 | 实验室复现环境条件 | 设计加固、客户侧改造 |
| **操作** | 特定用法/顺序/负载 | 按客户操作步骤复现 | 引导、限制、文档 |

判据：能说出一句带数字的结论，例如"这一批 32 台里 5 台，都是同批 PCB，都发生在低于 -10℃"。

做不到就先补数据，不要跳到"改代码试试"。

### F3 处置决策

四选一，写清代价：

- **规避**：改配置、降级功能、限制用法。代价：功能缺失，客户要知情。
- **远程升级**：有 OTA 能力时优先。代价：需要 `release` 的升级通道可靠。
- **返修**：单机问题。代价：物流与时间。
- **停用**：安全相关或无法规避。代价：客户业务中断，必须书面。

判据：**每种处置都写明风险与客户知情记录**。安全相关的问题不允许"先用着"。

### F4 回流（这一步决定下次还会不会发生）

每个现场问题结束，问一句：**哪一段本该拦住它？**

| 本该拦住的地方 | 回流动作 |
|---|---|
| 点亮阶段没发现 | 补 `sensor-bringup` 的对应层判据 |
| 设计时没算到 | 补 `design-budget` 的失败模式表 |
| 审查没抓出 | 补 `code-audit` 的层级判据 |
| 测试没覆盖 | 补 `board-test` 的 T1/T3 用例 |
| 发布没验证 | 补 `release` 的清单项 |
| 就是没想到 | 记 inbox，标 `信心：低`，等第二次复现 |

具体动作：记一行到 `learnings/inbox.md`，格式同 `capture-learnings`。

### F5 修复验证

- **同 SN 复测**：原来那台必须好。
- **同批抽检**：同批次至少抽 3 台。
- **观察窗口**：至少 72 h 无复发，才能结案。
- **回归**：修复引入的新用例进 `board-test`。

判据：只在实验室那台好了，不算修好。

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "客户说不能用，先改代码" | 不知道现象就改，改的是猜想 | 先要 F0 信息包 |
| "日志里看不出来" | 说明黑匣子缺失 | 补事件记录，再谈定位 |
| "只有一台，个案" | 个案和批次早期长得一样 | 先看批次与出厂时间 |
| "返修回来就好了" | 根因可能还在其他机器上 | 追根因，否则下次批量爆 |
| "先让客户用着，下版修" | 安全相关问题不能这么处理 | 评估风险，必要时停用 |
| "这个问题很怪，复现不了" | 复现不了通常是信息不够 | 补采集项，不是放弃 |

## 红旗

- 开始改代码时，手上没有 F0 信息包
- 不知道故障设备的固件 SHA
- 没有黑匣子，或黑匣子只有自由文本
- 结案时没有同批抽检
- 同一个问题第二次出现，但上次没记 inbox
- 停用/规避没有客户书面确认
- 返修件回来只换了板子，没做根因分析

## 验收（现场问题可以结案了）

- [ ] 信息包完整，能写出复现步骤
- [ ] 归因到四级之一，结论带数字
- [ ] 处置方式与代价已记录，客户知情
- [ ] 回流动作已执行（判据/用例/清单至少补一处）
- [ ] 同 SN 复测通过
- [ ] 同批抽检 ≥ 3 台通过（无产线批次记录时，退化为同型号任取 3 台）
- [ ] 观察窗口 ≥ 72 h 无复发
- [ ] 修复引入的用例已进 `board-test`
- [ ] 经验已按 `capture-learnings` 记入 inbox

## 使用后沉淀（每次都用）

结案时记一行，重点写"哪一段本该拦住"：
