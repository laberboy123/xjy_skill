# 器件点亮（sensor bringup）

## 概述

点亮失败时最常见的成本不是"不会"，而是**跳层**：读不到 0xFF 就去怀疑上拉，接着怀疑芯片坏，然后重写驱动——同时改三个变量，最后不知道哪个起作用，于是一个点卡三天。

本流程把点亮拆成 **L0–L6 七层**，每层有明确的通过判据和"不通过时允许做什么"。核心规则只有三条：

1. **一次只进一层，不通过不许往下走。**
2. **一次只改一个变量，改前先写假设。**
3. **每层 30 分钟时间盒，超时写证据、换层或换工具，不换猜想。**

判据必须由仪器输出、寄存器回读、日志或代码运行结果支撑。**"应该是……"不算证据。**

## 何时使用

- 新板首次上电，要确认板上每一颗 I2C/SPI/UART 器件是否可用
- 已知能用的驱动换到新板/新批次/新供应商器件上不工作
- 现场或返修板反馈"某传感器没数据"
- 器件能读到数据，但你不确定它是否"真的对"（这一条最容易漏）

**不适用**：纯硬件设计评审、射频/电源完整性分析、需要示波器以外的专用设备的失效分析（这些交给硬件团队）。

## 流程

### Step 0：先建最小验证工程（省时间最多的一步）

在动手前，建一个**只做一件事**的固件工程：

- `probe_id`：只读器件 ID，其它一律不做
- `dump_regs`：只把寄存器表打印出来
- `read_raw`：只按固定周期打印原始值

**绝不在应用工程里 debug 驱动。** 应用工程有 RTOS、有业务任务、有别的器件在抢总线，任何现象都可能是耦合出来的。最小工程是你的对照组。

同时在 `bringup-log.md`（本技能目录里的模板）复制到项目 `.embedded/bringup-log.md`，建一份证据日志，四列：假设 / 改了什么 / 观察到什么 / 结论。每一行必须能被第三个人复现。

### Step 1：L0 供电与物理层

| 项 | 要求 |
|---|---|
| 目标 | 确认"板子本身是活的"，把硬件问题在固件之外切掉 |
| 工具 | 万用表（断电阻抗、上电电压）、原理图、datasheet 的 typical application |
| 通过判据 | 断电量 VDD–GND 阻抗在 kΩ 量级不短路；上电 VDD/VDDIO 在 datasheet 范围 ±5%；IO 电平与主控一致（3.3V 器件接 5V 主控 = 停）；I2C 上拉存在且阻值匹配速率与总线电容；SPI 的 CS 有上拉；INT/DRDY 有上拉或推挽；地址选择脚接法符合预期地址 |
| 不通过时 | **停。** 改板、飞线、换料、找硬件。不允许用固件绕 |

证据物：电压实测值、阻抗实测值、原理图截图（标出你量的点）。

### Step 2：L1 总线波形

| 项 | 要求 |
|---|---|
| 目标 | 确认线上有"正确的电信号"，而不是"看起来在跑" |
| 工具 | 逻辑分析仪（优先，能解码 I2C/SPI）、示波器 |
| 通过判据 | I2C：起始/停止条件完整；每个字节后 ACK 位被从机拉低；上升时间满足速率要求（100k 需 ≲1µs，400k 需 ≲300ns，按总线电容核算）；无异常 clock stretching。SPI：CPOL/CPHA 与器件一致；CS 建立/保持时间满足 datasheet；MISO 不浮空 |
| 不通过时 | 降速（400k→100k）先验证是不是时序问题；调上拉阻值；用 GPIO bit-bang 做对照实验；SPI 改模式逐个试 |

**禁止**：在这一层改寄存器配置或驱动逻辑。波形不对，配置写得再对也没用。

证据物：波形截图（含解码结果）、总线速率、上拉阻值。

### Step 3：L2 器件应答

| 项 | 要求 |
|---|---|
| 目标 | 确认芯片在说话 |
| 工具 | Linux: `i2cdetect -y <bus>` / `spidev_test`；RT-Thread: msh 里的 i2c 命令或自己写 probe；裸机: 最小工程的 `probe_id` |
| 通过判据 | I2C 地址被扫到（常见 7 位地址区间 0x08–0x77，具体看 datasheet）；`WHO_AM_I` / chip ID / 版本寄存器与 datasheet 标称值一致 |
| 不通过时 | 查地址脚/CS 是否被别的器件共用；查是否在错误的电源域（有些器件有独立 VDDIO）；**拿官方 EVK 或已知好板交叉验证**——同样代码在 EVK 上通、在你的板上不通，问题就锁定在板子；反之锁定在代码 |

**禁止**：读不到 ID 就改驱动。ID 都读不到，驱动里的任何逻辑都不会让它变得能读到。

证据物：地址扫描输出、ID 寄存器原始返回值（十六进制）、datasheet 对应页截图。

### Step 4：L3 复位与寄存器回读

| 项 | 要求 |
|---|---|
| 目标 | 确认"写进去了"，而不是"我以为写进去了" |
| 工具 | `dump_regs` + datasheet 的 register map / reset value 表 |
| 通过判据 | soft reset 后所有寄存器等于 datasheet 的 reset value（逐项比对）；每个要配置的寄存器 write → readback 一致；能读回说明地址自增/位序/大小端都正确 |
| 不通过时 | 查 SPI 的读写位（最高位是 R/W 还是地址最高位）；查 I2C 的寄存器地址宽度（8 位还是 16 位）；查多字节读写是否自动自增；查大小端与位序 |
| 注意 | 有些寄存器是只写的、有些读回值会被硬件改写（状态位），这类要在日志里标注"预期不可回读"，不要当成 bug |

证据物：reset 后的完整寄存器快照（十六进制 dump）、配置后的回读快照、与 datasheet 的逐项对照结论。

### Step 5：L4 数据通路

| 项 | 要求 |
|---|---|
| 目标 | 确认数据"随物理量动"，而不是"有数就行" |
| 工具 | `read_raw` + 物理激励（遮挡、加热、按压、转动、靠近、注水……取决于器件） |
| 通过判据 | DRDY/INT 按预期频率到来（用示波器量或数中断计数）；FIFO 计数递增；原始值随激励**单调、可重复**变化；零点与噪声水平在 datasheet 规格内；量程没有溢出 |
| 不通过时 | 查 ODR/量程/滤波/低功耗模式配置；查激励方式是否足够（很多"数据不动"其实是激励不够）；查是否读到了影子寄存器或旧数据 |
| 注意 | **"能读到数据" ≠ "能用"**。恒定值、缓慢漂移的固定值、随温度无关的假值，都通过不了这一层 |

证据物：原始值随激励变化的记录（时间序列或前后对比）、噪声/零点的实测数字。

### Step 6：L5 驱动健壮性

| 项 | 要求 |
|---|---|
| 目标 | 异常情况下不挂死 |
| 工具 | 故障注入：拔掉器件、短接总线、注入 NACK、返回错误 CRC、制造超时 |
| 通过判据 | 每次异常都有超时返回而不是死等；错误能被上层感知（返回码/状态位/日志）；恢复后能重新工作（不需要重启）；连续 1 小时无丢帧、无总线锁死 |
| 不通过时 | 补超时（每个阻塞点都要有）、补重试与退避、补总线恢复（I2C 的 9 个时钟脉冲解锁）、补状态机 |
| 平台要点 | Linux：注意 `ioctl` 返回值与 `errno`；RT-Thread：`rt_i2c_transfer` 返回长度要校验；FreeRTOS/裸机：自己实现的超时必须用计数而不是死循环 |

证据物：故障注入前后的日志对比、恢复时间、1 小时稳定性统计（帧数/错误数）。

### Step 7：L6 集成

| 项 | 要求 |
|---|---|
| 目标 | 能在应用里用，而不是只能在最小工程里用 |
| 通过判据 | 采样率达标且稳定；时间戳对齐（与系统时基无累积漂移）；单位/坐标系/量程换算正确（用已知物理量反算验证）；8 小时漂移在规格内；与其它器件共存时总线无冲突 |
| 不通过时 | 回 L4 重查数据质量；检查总线仲裁/优先级；检查任务调度周期与抖动 |

### 时间盒与停止规则

- 每层 **30 分钟**。超时后必须做三件事：写一行证据日志、把当前假设记下来、然后**换动作类型**（换工具 / 换层做对照 / 找人 / 拿 EVK）。
- **连续两次超时**：停手，把证据整理成一页交给别人看。卡住的人往往缺的是"一个没被自己污染过的视角"，不是更多时间。
- 任何时候发现自己在"改代码试试看"而不是"验证一个假设"，立刻停。

## 平台差异速查

| 平台 | 注意点 |
|---|---|
| Linux | `i2cdetect -y -r <bus>`；`i2cget/i2cset` 做寄存器级验证；`spidev` 注意 `SPI_IOC_WR_MODE` 与 `spi_ioc_transfer` 的 `speed_hz`；设备树里 pinctrl/上拉配置错会表现为"硬件问题" |
| RT-Thread | 优先用 `rt_i2c_transfer`/`rt_spi_transfer` 的消息结构，别自己拼时序；msh 里 `/sys` 或 `list_device` 先确认设备注册成功；`rt_pin_` 配置上拉在部分 BSP 上不生效，要查 pinctrl |
| FreeRTOS | 中断里只做通知，读寄存器放到任务；`vTaskDelayUntil` 保周期；I2C 驱动里的超时不要用 `vTaskDelay` 死等，用信号量 + 超时 |
| 裸机 | 先用 GPIO bit-bang 跑通一颗，确认波形和地址，再换硬件外设；bit-bang 是最便宜的逻辑分析仪替代品 |

## 常见合理化（以及反驳）

| agent 或你自己会说 | 为什么不行 | 应该做 |
|---|---|---|
| "应该是上拉电阻的问题" | 没测就是猜 | 示波器量上升时间或直接换阻值做单变量对照 |
| "这颗芯片可能是坏的" | 这是最贵也最少的结论 | 先拿 EVK 交叉验证；同一代码在 EVK 上通就说明芯片没坏 |
| "驱动是从别的项目抄的，应该没问题" | 寄存器默认值和器件批次会变 | 打印 reset 后快照，与 datasheet 逐项比对 |
| "数据能读出来就说明通了" | 恒定值也能读出来 | 必须做 L4 的物理激励验证 |
| "先写应用逻辑，驱动后面再调" | 会把总线问题和业务问题耦合在一起 | 先把最小工程跑通，且只跑这一个器件 |
| "改一下试试" | 同时改多个变量后，观察结果无法归因 | 先写假设，只改一个变量，改完只回答假设成立与否 |

## 红旗（出现即说明流程被违反）

- 在 L2 之前修改了驱动代码
- 一轮里改了两个以上变量
- 证据日志里出现"可能是""应该是"，但没有对应的测量
- 用应用工程而不是最小工程排障
- 没有波形就去调寄存器
- 把"能读到 ID"当成"点亮完成"
- 某一层待了超过两小时，但没有向任何人同步过现状

## 验收（点亮结束的出口）

全部满足才算点亮完成，缺一项就是没完成：

- [ ] 器件 ID 读取可稳定复现（连续 100 次无失败）
- [ ] reset 后寄存器快照与 datasheet 一致，配置项全部回读通过
- [ ] 原始值随物理激励单调变化，零点/噪声/量程有实测数字
- [ ] 故障注入后能超时返回并恢复正常，1 小时无丢帧
- [ ] 应用侧采样率、时间戳、单位换算已验证
- [ ] `bringup-log.md` 已归档，含波形截图与寄存器快照
- [ ] 本次踩的坑已按 `skill-curator` 的格式记入 `learnings/inbox.md`
- [ ] 若该坑已复现两次或造成过一天以上返工，已提议写进本文件对应层或 `layered-bringup.md`

## 使用后沉淀（每次都用）

点亮结束后，把本次新发现按一行格式追加到 `learnings/inbox.md`：

```
2026-11-20 | sensor-bringup | L2 | SPI / BMP390 | 现象：ID 读到 0x00 | 证据：MISO 无驱动，示波器截图 w3 | 建议：坑位表加"MISO 浮空" | 信心：高
```

只记两类：

1. **判据失效**——判据说通过但后面出事（该拦没拦），或判据说会挂但实际没事（误拦）。
2. **现有分层没覆盖**的现象、器件、平台差异。

**不要直接改本文件的判据。** 判据是这个技能的"真相"，改动要走 `skill-curator` 的两次复现门槛 + 人工批准，否则一次偶发就会被写死成规则。
