# 代码审计（code audit）

## 概述

普通 review 看"写得对不对"，嵌入式还要多看三件事：**资源会不会用尽、时序会不会破、指针会不会飞**。前两个在桌面程序里最多是变慢，在你这里一旦发生就是死机——往往还在现场、在客户手里。

审计按 **A0–A7 八层**走，每层给"查什么 / 怎么查 / 判据"。

一条执行原则：**先跑机器，再用人眼**。编译器告警和静态分析能白捡掉一半问题，剩下的才值得你逐行看。

## 何时使用

- 驱动或应用代码合入前
- 新增任务/线程，或改了优先级、锁、栈大小
- 现场出现 HardFault、随机复位、偶发死机、数据错乱
- 交付/上线前体检
- 换编译器、换优化等级、换 RTOS 版本——大量 UB 会在这个时刻才暴露

**不适用**：纯硬件设计、纯 UI 布局、Python 上位机（后者走 `board-test` + 普通 review）。

## 流程

### Step 0：先跑机器

命令清单见 `commands.md`。顺序固定：

1. **编译告警清零**（`-Wall -Wextra -Wshadow -Wconversion`），不要有"这个告警没事"的例外
2. **静态分析**：`cppcheck`、`clang --analyze`（或 `-fanalyzer`）
3. **grep 高危点**：`malloc|free|memcpy|strcpy|sprintf|alloca|TODO|FIXME`
4. 才进入人工读逻辑

**告警没清零不要进入 A0。** 否则你会花两小时发现一个 `-Wformat` 早就报过的问题。

### A0 内存申请方式

- **查什么**：每一处动态申请的**生命周期**。
- **怎么查**：`grep -n "malloc\|calloc\|realloc\|free\|rt_malloc\|pvPortMalloc\|k_malloc"`，逐个标注"哪个阶段申请、谁释放、失败怎么办"。
- **判据**：
  - 运行期不再申请（只在初始化阶段申请）。做不到，就要有上限、有失败分支、有碎片评估。
  - 每处申请都判空。
  - 释放后指针置 `NULL`，无 use-after-free、无双重释放。
  - 中断/回调里没有动态申请。
  - DMA buffer：对齐、不在栈上、cache clean/invalidate 已处理。
- **高危模式**：`sizeof(ptr)` 当 `sizeof(*ptr)`；循环里申请不释放；VLA（`uint8_t buf[n]`）与 `alloca`；结构体含指针却按值拷贝；申请大小可被外部输入控制。

### A1 栈与栈溢出

- **查什么**：每个任务栈是否够、中断路径是否吃栈。
- **怎么查**：**实测高水位，不靠估算**。
  - FreeRTOS：`uxTaskGetStackHighWaterMark()`，开 `configCHECK_FOR_STACK_OVERFLOW=2`
  - RT-Thread：`list_thread` 看 max used
  - 裸机：栈区启动填 `0xA5`，跑完全流程扫最大使用位置
  - 编译期：`-fstack-usage`（生成 `.su`）+ `-Wstack-usage=1024`
- **判据**：**实测峰值 ≤ 配置值的 70%**。超过就是不够。
- **高危**：局部大数组（> 256 B 要能解释）；`printf/sprintf`（浮点格式化轻松吃 1–2 KB）；递归与深调用链；ISR 里跑重活；假设"中断有独立栈"（Cortex-M 只有 MSP/PSP，主栈与中断栈常常是同一块）。

### A2 线程优先级分布

- **查什么**：一张表，不是一个感觉。没有这张表就谈不上审计：

| 任务 | 优先级 | 周期/事件 | 最坏执行时间 | 阻塞点 | CPU 占比 |
|---|---|---|---|---|---|

- **判据**：
  - 优先级**唯一**（同优先级分片会带来不可复现的抖动）。
  - 截止期越短优先级越高（RM 的基本要求）。
  - 有 CPU 占用**实测值**（`vTaskGetRunTimeStats` / `cpuusage` / GPIO 翻转测占空）。
  - Cortex-M 的 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 与临界区匹配——配错会让"关中断保护"完全失效。
- **高危**：全部任务同优先级（等于没有调度策略）；ISR 唤醒的任务优先级低于当前运行任务，响应被推迟；完全没有 CPU 占用数据。

### A3 互斥锁配置

先对**选型**，再谈配置：

| 场景 | 正确原语 | 错误做法 |
|---|---|---|
| 任务间保护共享数据 | mutex（带优先级继承） | 二值信号量（无继承，会反转） |
| 任务与 ISR 共享 | 临界区/关中断；或 ISR 只投递队列 | 在 ISR 里 take mutex（非法） |
| 事件通知 | 信号量/事件组/队列 | 用 mutex 当通知 |
| 一次性初始化 | 静态初始化，或启动时初始化一次 | 每次使用前 init |

- **判据**：
  - 每个锁有文档：谁持有、最长持多久、申请失败怎么退。
  - 有全局**加锁顺序表**（避免 A→B / B→A 死锁）。
  - 持锁期间不调用可能阻塞的函数（log、I²C、`delay`、`malloc`）。
  - 关中断最大时长有实测值（建议 < 20 µs，按你的实时性要求定）。
- **高危**：ISR 里用非 `FromISR` 版本；早退路径漏 `give`；递归拿同一把非递归锁；临界区里做长活。

### A4 非法地址

- **查什么**：指针的每一次解引用、每一次算术。
- **判据**：
  - 外部输入（协议长度、索引、偏移）进入指针运算前必须做范围校验。
  - 所有 `memcpy/strcpy/sprintf` 有长度或 `sizeof` 保护。
  - 每个可能返回 `NULL` 的调用都有判空路径。
  - 对齐正确（`uint32_t*` 指向非 4 字节对齐地址，在 M0/M3 直接 HardFault）。
  - 寄存器访问有 `volatile`；不跨编译器假设位域顺序。
- **高危**：`free` 后继续用、双重释放；越界写（`<=` 循环、off-by-one）；指针类型双关（strict aliasing）；把结构体地址强转成别的类型再读写。

### A5 阻塞与时序

- 每个阻塞调用都有超时；`portMAX_DELAY` 必须有理由
- 没有忙等（`while(!flag);`）
- ISR 里没有 `delay`/`printf`/长循环
- 关中断时长有实测
- 喂狗点覆盖所有关键任务，不是只在一个任务里喂

### A6 错误处理与资源

- 每条失败路径都有处理，包括"初始化失败是否继续跑"
- 错误码没有被 `(void)` 吞掉
- Linux 侧 fd/句柄/socket 都有 `close`，早退路径不漏
- 状态机有 default/非法状态处理
- `assert` / `configASSERT` 在 release 配置下的实际行为是清楚的（别假设它一定生效）

### A7 可观测性

- 有错误计数、栈水位、堆水位、CPU 占用、复位原因
- 日志分级，ISR 里不直接打印
- 有 POST 自检（与 `board-test` 呼应）

## 报告

用 `audit-report.md`。三条硬规则：

1. 每条必须有**位置（文件:行）**和**触发条件**；说不清触发条件的，降为 P3 或删掉。
2. 严重度只有四档，不许自创（见模板定义）。
3. 不写"建议使用静态分析"这类空话，写出来必须能直接改。

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "代码能跑就行" | 跑通只覆盖了 happy path，你的故障都在异常路径 | 按 A5/A6 走一遍失败路径 |
| "这个任务不会阻塞" | 没有证据就是猜测 | 看它调用的每个函数有没有阻塞点 |
| "已经用 mutex 保护了" | ISR 里根本拿不到 mutex | 确认访问方是任务还是 ISR，选对原语 |
| "栈给 4K 够了" | 估算经常差 2–3 倍 | 测高水位，看 70% 线 |
| "malloc 失败很少见" | 少见，但一旦发生就是 HardFault | 每处判空，或改成静态分配 |
| "编译器会优化掉" | 优化掉的可能是你要的副作用 | 加 `volatile`，别靠编译器"聪明" |
| "以前都这么写" | 换编译器/优化等级/RTOS 版本就炸 | 拿本次的实测数字说话 |
| "静态分析误报太多" | 误报也比漏报便宜 | 分类处理，别整体关掉 |

## 红旗（出现即说明审计没做完）

- 没有优先级表，或表里优先级有重复
- 没有加锁顺序表
- 栈水位、CPU 占用没有任何实测数字
- `grep` 到 ISR 里调用 `xSemaphoreTake` / `mutex_lock`
- 存在无超时的阻塞调用，且没有注释说明为什么
- `malloc` 遍布运行路径，且没有失败分支
- `memcpy` 的长度来自外部输入且无校验
- 编译告警还有残留
- 报告里全是"建议加强""注意风险"这类不可执行的句子

## 验收（审计可以结束了）

- [ ] 编译告警清零
- [ ] cppcheck / clang-tidy 至少跑过一次，结果已逐条分类
- [ ] 每个任务的栈高水位有实测数字
- [ ] CPU 占用有实测数字
- [ ] 优先级表存在，且优先级唯一
- [ ] 加锁顺序表存在，持锁时长有上界
- [ ] 所有动态申请都有生命周期结论（谁释放/为何不释放）
- [ ] 所有外部输入进指针运算前有校验
- [ ] P0/P1 每条都有结论：修复 / 接受（写明理由）/ 延期（写明责任人与日期）
- [ ] 报告已归档到项目证据目录

## 使用后沉淀（每次都用）

审计结束，把那句"下次 5 分钟就能查出来"的记一行到 `learnings/inbox.md`：

```
2026-11-20 | code-audit | A3 | FreeRTOS | ISR 里 take mutex 导致偶发死锁 | 现场 log + 栈回溯 | A3 判据补"grep FromISR 反查" | 高
```

重点记两类：**判据漏掉的模式**（这次没查到、后来出事的）和**误报**（报了但实际无害的）。不要直接改判据，走 `skill-curator`。
