# 方案与资源预算（design budget）

## 概述

`customer-spec` 回答"做什么"，本技能回答"**用什么资源、按什么结构做**"。

它存在的唯一理由：`code-audit` 要求优先级表和加锁顺序表，`board-test` 要求资源预算——**这些表没人产出，审计就只能看见什么审什么**。设计段的输出被后面三段直接消费，是整条链的接口。

判断你有没有跳过这一步，只看一句话：**你能立刻说出"RAM 用了多少、还剩多少"吗？** 说不出来就是在裸奔。

## 何时使用

- spec 已确认，动第一行代码之前
- 新板首版方案（哪怕只做一个小功能）
- 需求大改，需要重排任务或超预算
- 换 MCU / 换 RTOS / 换编译器的移植方案
- 现场出现"资源耗尽"类问题（堆碎片、栈溢出、CPU 跑满），需要重算账

**不适用**：改一个常量、修一个明确的 bug（直接改，别套流程）。

## 流程

### 最小起步：先做三张，别被六张吓住

不是每个项目都要一次补齐六表。按"现在要干什么"决定顺序：

| 现在的动作 | 必须先有的表 | 可以后补的 |
|---|---|---|
| 开始写代码 | D1 预算、D2 优先级、D3 接口 | D4 协议、D5 失败模式、D6 可观测性 |
| 联调/集成 | D4 | D5、D6 |
| 交付前 | D5、D6 | — |

**只上电点器件时，不需要先做 design-budget。** `sensor-bringup` 不依赖预算表——它的 L0 就是硬件检查，那张"点亮出口清单"是它的**产出**，不是它的输入。别把产出当前置去补。

判据：任何时刻，你手上至少有"正在用的那张表"。缺表开工 = 后面返工。
### D1 资源预算表（先算账，再写码）

| 资源 | 总量 | 预算 | 余量 | 依据 |
|---|---|---|---|---|
| Flash | ___ KB | ___ KB | ≥20% | 现有固件实测 + 新功能估算 |
| RAM（静态） | ___ KB | ___ KB | ≥30% | 全局/静态变量 + 缓冲 |
| 栈合计 | ___ KB | ___ KB | ≥30% | 见 D2 |
| 堆 | ___ KB | ___ KB | — | 优先 0；非 0 要有理由 |
| CPU | 100% | ___% | ≥30% | 见 D2 的最坏执行时间 |
| 功耗（平均） | ___ mA | ___ mA | ≥20% | 各模式电流 × 占空 |
| 引脚 | ___ | ___ | — | 含复用冲突 |
| 定时器/外设 | ___ | ___ | — | 含 DMA 通道 |
| 中断优先级段 | ___ | ___ | — | 与 RTOS 可管理段分开 |

判据：

- 每项都有**数字**，不许写"够用"。
- 余量低于阈值就要在表里写清"为什么可以接受"。
- 堆优先为 0。非 0 必须写：申请上限、失败策略、碎片评估方式。

### D2 任务划分与优先级表

**先按周期/事件划分，不要按功能划分。**"温控功能"不是一个任务；"每 100ms 采样的控制环"和"每 5s 上报的通信"是两个任务。

| 任务 | 职责 | 优先级 | 周期/事件 | 最坏执行时间 | 栈初值 | 通信方式 | 阻塞点 |
|---|---|---|---|---|---|---|---|
| 控制环 | | 3 | 100ms | ___ µs | 512B | 队列 | 无 |
| 采集 | | 2 | 10ms | | | 队列→控制环 | |
| 通信 | | 1 | 5s / 事件 | | | 队列 | 等发送完成 |

判据：

- 优先级**唯一**，按"截止期越短越高"排（RM）。
- 栈初值 = 估算最大值 × 1.5，且不低于 512B；**估算要包含 `printf` 类库函数的峰值**。
- 每个任务写出"最坏执行时间"的量级（µs/ms 都行），写不出说明还没想清楚。
- 任务之间只通过队列/事件/共享数据 + 锁交互，**不允许直接互相调用**。

> 这张表就是 `code-audit` A2 的输入，审计时直接取用，不再现场编。

### D3 模块边界与接口

分三层，依赖单向：

```
应用层（业务、状态机、判定）
   ↓ 只依赖接口
服务层（设备管理、协议、存储、调度）
   ↓ bus_ops / dev_ops
驱动层（寄存器操作，不感知业务）
```

必须定下来的接口：

```c
/* 驱动只依赖这组指针，便于 board-test T1 打桩 */
struct bus_ops {
    int (*read)(void *ctx, uint8_t reg, uint8_t *buf, size_t len);
    int (*write)(void *ctx, uint8_t reg, const uint8_t *buf, size_t len);
    void *ctx;
};
```

判据：

- 驱动层不 `#include` 任何业务头文件。
- 业务层不直接访问寄存器。
- 每个接口写明：入参范围、返回值含义、是否可重入、失败时状态。

### D4 协议、状态机与错误码

- **帧格式**：给一个真实的十六进制样例，不只是字段表。
- **状态机**：画出来（哪怕是 ASCII），列出所有状态 × 事件的迁移；**每个状态都要有非法事件的处理**。
- **错误码表**：一个码对应一个可执行的处置动作，不许有"未知错误"。
- **超时与重试**：每个等待点写超时值、重试次数、重试后行为。

### D5 失败模式表

直接对齐 spec 第 8 段的每一条：

| 失败源 | 检测方式 | 产品行为 | 恢复方式 | 恢复时间 |
|---|---|---|---|---|
| 传感器无响应 | 连续 3 次超时 | 用上次有效值 + 置故障位 | 下一周期自动重试 | ≤ 1 个周期 |
| 总线挂死 | 连续 NACK | 总线复位（9 脉冲） | 成功则恢复，失败降级 | ≤ 500ms |
| 通信中断 | 心跳超时 10s | 本地缓存，恢复后补传 | 重连 | ≤ 30s |
| 掉电 | — | 重启后自检并恢复默认 | 上电自检 | ≤ 2s |

判据：**spec 第 8 段有几条，这里就有几行**。缺一行就是少想了一个场景。

### D6 可观测性设计

- 日志：分级（ERROR/WARN/INFO/DEBUG），什么时候打、打什么字段
- 计数：通信错误、超时次数、复位原因、栈水位、堆水位
- 自检：上电 POST 检查哪些项、失败后怎么表现
- 喂狗：几个喂狗点、各自代表什么还活着

判据：**出问题时，能不能只靠日志和计数定位到模块？** 不能就补。

### D7 设计评审（自查即出口）

六张表齐全后跑一遍：

- [ ] 预算总和 ≤ 硬件；每项余量达标或有理由
- [ ] 优先级唯一，且与截止期顺序一致
- [ ] 所有功能都能映射到某个任务（没有"没人管"的功能）
- [ ] 每个跨任务共享数据都有主
- [ ] 失败模式表覆盖 spec 第 8 段全部条目
- [ ] 每个状态机状态都有非法事件处理
- [ ] 每个阻塞点都有超时

评审通过后，方案**锁定**。之后改它走 `customer-spec` 的变更单。

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "先写，写完再看资源" | 写完才发现 RAM 不够，就得重构 | 先出预算表，10 分钟 |
| "就一个功能，不用设计" | 一个功能也要占任务、栈、优先级 | 至少填 D1 + D2 两行 |
| "优先级按顺序给 1、2、3 就行" | 顺序不等于截止期顺序 | 按最坏执行时间/周期算 |
| "栈给 1K 是惯例" | 惯例不是依据 | 算 `printf` + 调用深度，再乘 1.5 |
| "任务按功能分最自然" | 功能之间没有调度含义 | 按周期/事件分 |
| "错误码先随便定" | 上层要按错误码决定动作 | 一个码一个处置动作 |
| "设计文档没人看" | 审计和测试都要读它 | 六张表就是交接契约 |

## 红旗

- 说不出当前 RAM/Flash 用了多少
- 优先级表不存在，或存在但优先级有重复
- 任务按"功能模块"命名（`temp_task`、`display_task`），而不是按周期
- 每个任务都写"栈 1K"且没有依据
- 失败模式表比 spec 第 8 段条目少
- 状态机只画了正常路径
- 接口没有写明失败返回值

## 验收（设计可以交付了）

- [ ] D1 预算表每项有数字，余量达标或有书面理由
- [ ] D2 任务表完整，优先级唯一，栈初值有推导
- [ ] D3 分层单向依赖，`bus_ops` 已定义
- [ ] D4 有真实报文样例、状态机全迁移、错误码表
- [ ] D5 失败模式覆盖 spec 第 8 段
- [ ] D6 日志/计数/POST/喂狗四点齐
- [ ] 设计已锁定，变更走变更单
- [ ] 三张表（预算、优先级、失败模式）已交给 `code-audit` 与 `board-test`

## 使用后沉淀（每次都用）

设计评审后，把"这次算漏了什么"记一行到 `learnings/inbox.md`：

```
2026-11-20 | design-budget | D2 | STM32F4 + FreeRTOS | 按 1.5 倍估栈仍溢出，printf 占 1.4KB | map 文件 .su 数据 | D2 判据补"含格式化输出时 ×2" | 高
```

重点记两类：**预算估算偏差**（估了多少、实际多少）和**遗漏的设计维度**（评审时才发现必须补的）。偏差数据攒够三条，就可以回头修 D1/D2 的系数。
