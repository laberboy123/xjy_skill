# 发布与产线（release）

## 概述

发布的本质不是"把固件烧进去"，而是三件事：

1. **可追溯**——每个出货单元都能说出它跑的是哪个提交、哪个构建。
2. **可回滚**——升级失败能退回上一个可用版本，且现场做得到。
3. **可独立验证**——判定必须来自读回与实测，不是烧录工具自己的"成功"提示。

第三条是最容易糊弄、后果最严重的一条。借 pstack 的一条铁律：**命令报成功不等于成功**——它合并 PR 时要求回读实际状态，因为"排队成功"和"已合并"是两件事；在你这里，"烧录成功"和"这块板子真的在跑新版本"也是两件事，**必须回读版本号才算数**。

## 何时使用

- 首次向客户交付
- 任何固件版本发布（哪怕只改一行）
- 做 OTA / 远程升级功能
- 导入或修改产线测试流程
- 返修件、退换件重烧
- 现场要求"升级一下试试"

**不适用**：实验室自用改代码（直接烧，别套流程）。

## 流程

### R0 版本与构建可追溯

- **单一版本源**：`git describe --tags --dirty` 或 CI 注入，生成 `version.h`，**禁止手改**。
- **构建可复现**：工具链版本固定并记录；用 `SOURCE_DATE_EPOCH` 去掉构建时间戳差异；构建号 = 提交短 SHA。
- **固件内可查询**：开机日志或 `id` 命令必须能读出：版本号、git SHA、构建日期、硬件版本（hwrev）。
- **产物命名**：`<product>_<hwrev>_v<semver>_<sha7>.bin`，一把梭全带齐。

判据：随便拿一块板子，**30 秒内**能说出它跑的是哪个提交。做不到，后面所有支持工作都会退化成考古。

### R1 变更记录

两份，不要混：

- **面向客户**：新增/修复/行为变化，用客户能懂的话，不写内部实现。
- **面向内部**：关联变更单号、影响模块、是否破坏性（协议格式、配置存储、校准数据格式）。

破坏性变更必须单独标出，并写明"升级后旧配置会怎样"。

### R2 出厂自检与产线

**产线和现场用同一套 POST 代码**，不要写两份——两份迟早不一致，而不一致的那天你无法判断是产品坏了还是测试写错了。

产线序列（每台）：

```
烧录 → 读回版本/SHA → 上电自检 → 写校准参数 → 回读校验 → 写 SN/绑定信息 → 记录归档
```

判据：

- 每个出货单元有记录：SN、固件版本与 SHA、hwrev、自检结果、校准值、工位、时间。
- 良率可统计；失败有明确错误码（不是"失败"两个字）。
- 校准数据写入后**必须回读校验**；只写不读等于没写。
- 夹具走文本命令通道（复用 `board-test` 的 `host-protocol.md`），不要做成只能手点的 GUI。
- 产线耗时与节拍有实测值——超时的工位会被跳过，跳过就等于没测。

### R3 升级与 OTA

包结构（最小）：

```
| magic | 版本 | hwrev | 长度 | CRC32 | 签名(可选) | 载荷 |
```

硬要求：

- **断电在任意点都必须能恢复到可用版本**。这是设计约束，不是测试项——靠 A/B 分区、备份区或带校验的追加写入实现。
- 升级前检查：hwrev 匹配、版本可比（防降级）、供电/电量充足、空间足够。
- 升级后**回读确认**：版本号 + CRC + 自检通过，三项都过才算成功；任何一项不过，自动回退并记录。
- 降级默认禁止；要允许就必须写明理由与保护条件。

判据：**在随机时刻断电 20 次**，每次都能启动到"旧版本可用"或"新版本可用"，不允许出现变砖。

**没有 OTA 的项目**（纯烧录交付）：跳过 A/B 分区与断电注入，但"回读确认"仍然适用——烧录后必须读回版本与 SHA，并在产线归档。门禁相应改为"烧录后回读一致率 100%"。

**只有单区、无备份区**的老平台：明确写出"变砖只能返修"，并在 `release-checklist.md` 里标出这是已知风险，不接受"应该没事"。

### R4 分批发布

借 agent-skills 的分批思路，改成硬件能用的粒度：

| 批次 | 规模 | 观测窗口 | 推进条件 | 回滚触发 |
|---|---|---|---|---|
| 样机 | 1–2 台 | 24 h | 自检全过、关键功能实测、无复位循环 | 任何一次启动失败 |
| 小批 | 5–20 台 | 72 h | 升级成功率 100%、无新增错误计数 | 升级失败率 > 1% |
| 全量/产线 | 全部 | 持续 | 小批结论稳定 | 现场故障率超基线 2 倍 |

指标口径先定好：升级成功率、自检通过率、复位次数/小时、新增错误计数、客户报障数。

### R5 回滚计划（发布前就写，不是出事再想）

必须写清：触发条件、回滚方式（A/B 切回 / 重烧）、数据与配置兼容性、**现场能不能自己回滚**、预计耗时。

判据：**回滚必须实际演练一次**。纸面回滚计划和没有回滚计划，在事故现场是同一个东西。

### R6 交付包

```
deliver_<product>_v<semver>/
├─ firmware/            本版 + 上一版（回滚用）
├─ flasher/             烧录工具与说明（含驱动）
├─ host/                上位机与命令协议说明
├─ production/          产线脚本、夹具说明、测试判据
├─ docs/                变更记录、校准说明、故障排查手册
└─ test-report/         审计报告、测试报告、验收记录
```

## 常见合理化（以及反驳）

| 会说 | 为什么不行 | 应该做 |
|---|---|---|
| "烧录工具提示成功就是成功了" | 它只说写进去了，没说能启动 | 读回版本 + 自检 |
| "OTA 测过一次没问题" | 断电时机是随机分布，测一次等于没测 | 随机断电注入 20 次 |
| "先发出去，有问题再回滚" | 没演练过的回滚在现场不可用 | 发布前演练一次回滚 |
| "产线不用记录，能跑就行" | 出问题时无法按批次归因 | 每台一条记录 |
| "自检通过就说明没问题" | 自检只覆盖你想到的项 | 自检 + 黑匣子（见 `field-support`） |
| "版本号无所谓" | 30 秒说不出提交，支持就靠猜 | 固件内可查询 |
| "降级应该允许，方便救砖" | 降级会带回已修的 bug 和不兼容配置 | 默认禁止，要开就写保护条件 |
| "产线我们自己人操作，不会错" | 人会跳过步骤，脚本不会 | 夹具脚本化 + 结果自动归档 |

## 红旗

- 固件里查不出版本/SHA
- 烧录后没有回读校验步骤
- OTA 没有断电恢复设计，只在测试里"注意别断电"
- 回滚计划只写在文档里，从没演练
- 产线测试靠人点界面，没有结果归档
- 校准数据只写不读
- 版本号靠手改 `version.h`
- 交付包里没有上一版固件（想回滚时发现没得退）

## 验收（可以发布了）

- [ ] 固件内可查版本、SHA、构建日期、hwrev
- [ ] 构建可复现（同提交 + 同工具链 = 同产物）
- [ ] 产线序列脚本化，每台有归档记录
- [ ] 校准数据写入后回读校验通过
- [ ] OTA 随机断电 20 次全部可恢复
- [ ] 升级后回读确认（版本 + CRC + 自检）
- [ ] 回滚已实际演练，耗时已记录
- [ ] 分批观测窗口与回滚触发阈值已写定
- [ ] 交付包结构完整，含上一版固件
- [ ] 客户文档不含内部实现细节，但含故障排查与升级步骤

## 使用后沉淀（每次都用）

发版后把"这次差点漏掉什么"记一行到 `learnings/inbox.md`：

```
2026-11-20 | release | R3 | STM32L4 + 双区 | OTA 在擦除后断电变砖，备份区未校验 | 现场返修 2 台 | R3 判据补"擦除阶段也要可恢复" | 高
```

重点记：**发布流程里被跳过的那一步**（事后证明它有用）和**回滚演练发现的坑**。
